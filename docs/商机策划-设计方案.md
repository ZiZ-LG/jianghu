# 商机策划 · 行动排期日历（设计方案）

> **定位**：在「侦探墙 / 干系人管理」之外，给客户工作台再装一个**孪生镜头**——把针对 G64111 低分项的销售动作、商机关键节点、历史触点，全部排到 **Apple Calendar 式的年/月/周日历**上：到期执行、周复盘、提分。
> **一句话**：侦探墙解决「**看清**」（关系网谁支持谁、哪项低分），商机策划解决「**做对**」（什么时间见谁、做什么、补哪一分）。二者共享同一份商机数据。
> **作用域**：**客户级**——进入某客户后，顶部 `ViewTabs` 切换「🕸 侦探墙 ｜ 📅 商机策划」，日历汇总该客户名下**所有商机**的行动/里程碑/触点。
> **状态**：方向已与 LG 对齐（2026-06-05）。本轮只出**方案 + HTML 原型**，不写功能代码。
> **分支**：建议 `feat/deal-planner`（从 main 切）。

---

## 0. 本质：补上 G64111 闭环缺的执行半环

`docs/产品设计方案.md` 定义的完整闭环：

```
G64111 诊断打分 → 趋赢力% → 741 选竞争策略 → 行动宝典取话术 → ★行动计划排期 → ★周复盘更新分数 →（循环）
                  └────────── 侦探墙已实现（看清） ──────────┘   └──── 商机策划要补（做对） ────┘
```

侦探墙只做了闭环的**前半段**。后半段「**行动计划排期 + 周复盘**」从未落地，而它正是销售方法论真正产出业绩的一环。商机策划日历 = 这后半段的可视化载体。

**它不是一个孤立的日程表**，而是 G64111 的执行面：日历上每一个「行动」都挂着一个**要补的低分项（gap）**和**一个要攻的人**，完成后回写复盘、推动趋赢力曲线上扬。

## 2. 与侦探墙的关系：两个镜头，一份数据

```
┌─ 客户：西部电力建设集团 ───────────────────────────────┐
│  顶部 ViewTabs：  [ 🕸 侦探墙 ]   [ 📅 商机策划 ]          │  ← 新增切换（客户级）
│ ────────────────────────────────────────────────────── │
│                                                          │
│   🕸 侦探墙（现有）              📅 商机策划（新增）         │
│   ─ 单商机 L1–L4 关系网          ─ 跨商机 年/月/周 日历      │
│   ─ 看清：谁卡谁、哪项低分        ─ 做对：何时见谁、补哪分    │
│   ─ 产出 gap（C/P/1K 缺口）  ───► ─ 把 gap 变成带日期的行动  │
│                          ◄─── 完成回写、周复盘推动趋赢力曲线 │
└──────────────────────────────────────────────────────────┘
```

- **不替换、不挪动侦探墙**：侦探墙仍是进入商机后的默认视图。商机策划是同级的第二个 Tab。
- **数据闭环联动**：侦探墙的趋赢力面板（`WinTendencyPanel`）每一个缺口项，都可「**＋排个行动**」一键在日历建一张 `PlanAction`（带 `gapItem`）。反向，日历里行动完成 → 触发该商机一张趋赢力快照（周复盘曲线）。

## 3. 三类日历事件 × 数据源（关键：两类现成）

| 事件类型 | 含义 | 数据源 | 时间锚 | 现状 |
|---|---|---|---|---|
| 🎯 **行动计划** | 我方要做的销售动作（拜访/对齐/送方案/攻关），关联某个 gap 与某个人 | **新表 `PlanAction`** | `dueDate` | ❌ 需新建（字段见 §4） |
| 🚩 **商机里程碑** | 商机自身的关键节点：预计签约、阶段推进、赢/输 | `Opportunity.expectedSignDate` / `status` / `pipelineStage` | `expectedSignDate` | ✅ 字段已在 schema |
| 📌 **历史触点** | 已发生的拜访/互动纪要（回看用） | `VisitNote` | `date` | ✅ 表 + `ADD_VISIT` + `VisitTimeline` 全现成 |

> 结论：整个模块**只需新增 `PlanAction` 一张表**。里程碑、触点都是「把已有数据换个时间镜头展示」。这是本方案落地成本低的根本原因。

## 4. 数据模型与契约

### 4.1 新增表 `PlanAction`（行动计划）

严格对齐 `产品设计方案.md §3.2 actions` 字段；**不用原生 enum/json**（铁律③跨库可移植），全 String。

```prisma
// 行动计划（G64111 闭环「行动排期」环的载体）。命名 PlanAction 以避免与前端 reducer Action 同名。
model PlanAction {
  id            String   @id // act_xxx
  tenantId      String
  accountId     String   // 冗余存，客户级日历直接按 accountId 聚合，免 join
  opportunityId String   // 必属某商机
  gapItem       String   @default("") // 关联 G64111 低分项：C1..C6 | P1..P4 | 1K（空=非补分动作）
  personId      String?  // 目标干系人（要攻的人），可空
  title         String                // 行动一句话（设计方案的 action 字段）
  scene         String   @default("") // 场景
  scripts       String   @default("") // 话术（741 行动宝典可预填）
  target        String   @default("") // 期望达成
  ownerId       String   @default("") // 负责人 userId（默认创建者）
  dueDate       String   @default("") // YYYY-MM-DD ← 日历主锚
  status        String   @default("todo") // todo | doing | done | skipped
  doneAt        String?               // 完成日期 YYYY-MM-DD
  review        String   @default("") // 复盘（完成后回填，喂周复盘）
  origin        String   @default("manual") // manual | ai（741 建议） | workbuddy
  createdBy     String   @default("")
  createdAt     DateTime @default(now())

  @@index([accountId])
  @@index([opportunityId])
}
```

> 改 schema 流程（CLAUDE.md）：动 `schema.prisma` → `npm run generate` → `npm run db:push` → **完全重启 node 进程**。

### 4.2 前端契约同步（store.ts = 权威）

新增 4 个 Action（对齐 `app/src/store.ts` 风格）：

```ts
| { type: 'ADD_PLAN_ACTION';    accId: string; oppId: string; action: PlanAction }
| { type: 'UPDATE_PLAN_ACTION'; accId: string; actionId: string; patch: Partial<PlanAction> } // 拖拽改期=patch dueDate
| { type: 'DELETE_PLAN_ACTION'; accId: string; actionId: string }
| { type: 'TOGGLE_PLAN_ACTION'; accId: string; actionId: string; done: boolean }              // 打勾完成→写 doneAt
```

后端 `mutate.ts` 对齐这 4 个写操作；`state.ts` 组装时把 `account.planActions[]` 挂到客户下（与 `visitNotes[]` 同款，按 accountId 查、不建 Prisma relation 也可）。

### 4.3 里程碑需要打通的现存「契约债」

`Opportunity` 的时间/规划字段在 **DB 里已存在，但前端链路没接通**——里程碑落地需补这三处：

| 字段（schema 已有） | types.ts | state.ts 组装 | mutate.ts UPDATE_OPP `pick` |
|---|---|---|---|
| `expectedSignDate`（预计签约日） | ❌ 缺 | ❓ 待确认 | ❌ 不在白名单 |
| `expectedAmountW`（金额·万元） | ❌ 缺 | ❓ | ❌ |
| `status`（active/paused/won/lost） | ❌ 缺 | ❓ | ❌ |

> 即：里程碑视图本身不需要新字段，但要把这条「DB→state→types→mutate」链路补齐，让前端能读写预计签约日。这是 V1 的一项明确工程任务（小、安全、属数据契约范畴，动手前按 CLAUDE.md 高风险区说明）。

### 4.4 触点：零改动

`VisitNote`（`date/topic/summary/participants/opportunityId`）+ `ADD/UPDATE/DELETE_VISIT` + `Account.visitNotes[]` 全部现成，日历直接读 `date` 投放。

## 5. 三视图规格（Apple Calendar 式）

统一框架：顶部 `CalendarHeader`（◀ 今天 ▶ ｜ 当前期标题 ｜ `年 月 周` 分段切换 ｜ ＋新行动）。视图偏好用 `usePersistentState('jianghu.plannerView', 'month')` 记住。

### 5.1 月视图（默认）— 作战全月一屏

- 6×7 网格，周一起始（大陆习惯，可配）；当前月实色、上下月日期淡灰；**今天**用 `--accent` 圆底日号。
- 每格按时间堆叠**事件胶囊**（chip）：🎯行动（按 gap/741 着色）、🚩里程碑（醒目描边）、📌触点（低饱和）。超出 3 条折叠为「**+N 更多**」，点开当日弹层。
- 顶部可选「**泳道按商机分组**」开关：同一商机的事件用左侧色条串起，跨商机统筹一目了然。
- 交互：拖拽 chip 改 `dueDate`（乐观更新 + `UPDATE_PLAN_ACTION`）；空格双击 = 当日建行动；点 chip = 右侧详情抽屉。

### 5.2 周视图 — 本周冲刺

- 7 列（日）。Apple Calendar 经典布局，但销售场景**弱化小时刻度**：默认按「全天事件」横条堆叠（拜访不像会议精确到分）；保留可选时间轴（V2）。
- 左侧细「未排期/逾期」轨：`dueDate` 已过且未完成的行动红色置顶，提醒补救。
- 适合「这周要推进哪 5 件事」的执行视角。

### 5.3 年视图 — 战役节奏俯瞰

- 12 个月缩略宫格（mini-month）。每月格内用**圆点热力**表示该月事件密度/构成（行动/里程碑/触点三色点）。
- 里程碑（预计签约日等）在年视图**始终可见**为标记点——一眼看清「哪几个月有签约窗口、节奏空档在哪」。
- 点某月 → 切月视图定位过去。

## 6. 视觉编码

复用产品语义 CSS 变量（`--panel/--ink/--line/--hover/--accent/--accent-soft…`），亮/暗主题自动适配；字体栈、圆角(8/10/12)、阴影(`var(--shadow)`)沿用现有约定。

| 通道 | 编码 |
|---|---|
| 事件类型 | 🎯行动 / 🚩里程碑 / 📌触点（图标 + 形态区分：行动实色胶囊、里程碑描边旗标、触点淡色） |
| 行动着色 | 按 `gapItem` 归类上色：6必清(C)=蓝系 · 4优势(P)=紫系 · 1决胜(1K)=金。一眼看出「这周在补哪类分」 |
| 状态 | todo 实色 / doing 进度纹 / done 置灰打勾 / skipped 删除线；**逾期未完成** 红角标 |
| 商机色条 | 泳道/chip 左侧 3px 色条 = 商机身份色（同一商机跨月同色） |
| 趋赢力 | 当日/当周聚合处可显该商机 `scoreFromDomain` 的趋赢力% + 741 band 底色（绝对优势绿/相对优势蓝/相对劣势橙/绝对劣势红） |

## 8. 核心交互

| 操作 | 行为 |
|---|---|
| 建行动 | 空格双击 / ＋按钮 / 侦探墙缺口「＋排个行动」→ `Modal` 填 title/人/gap/话术/截止 → `ADD_PLAN_ACTION` |
| 改期 | 拖拽 chip 到新日期 → 乐观更新 + `UPDATE_PLAN_ACTION{dueDate}` |
| 完成 | chip 勾选 → `TOGGLE_PLAN_ACTION{done}` 写 `doneAt`，置灰 → 提示「回填复盘」 |
| 看详情 | 点 chip → 右抽屉：行动全字段 + 关联商机/人/gap 跳转侦探墙 |
| 周复盘 | 周视图「本周小结」：完成项 + 趋赢力变化，可一键生成该商机 `score_snapshot`（曲线） |
| AI 建议 | 741 行动宝典产出动作 → 落「待排期建议」抽屉（`origin='ai'`，未进日历）→ 销售拖入某日才正式排期 |

## 10. 不碰的红线（对齐 CLAUDE.md 铁律）

1. **多租户隔离**：`PlanAction` 全程 `where { tenantId }`；`state.ts` 按 tenant+account 作用域查。
2. **AI 不自动写库**：741/AI 生成的行动**不直接进日历**，先入「待排期建议」，销售拖入排期=人审采纳（呼应铁律②精神；行动是我方动作非客户关系，但仍守人审边界）。
3. **跨库可移植**：`PlanAction` 字段全 String / Float / DateTime，**无 enum/json**（SQLite↔Postgres 一致）。
4. **winProbability 不碰**：日历趋赢力只读 `scoreFromDomain` 实时计算；销售手填的 `winProbability`、WorkBuddy 字段一律不写不覆盖。
5. **数据契约同步**：`PlanAction` 与里程碑字段的改动，前端 `store.ts`/`types.ts` 与后端 `mutate.ts`/`types.ts`/`state.ts` 同步落（铁律⑤）。
6. **BYO / 敏感**：本模块不引新密钥；行动话术若引用干系人敏感情报，沿用 `VisitNote`/FORM 既有可见性边界。
