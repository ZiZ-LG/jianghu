# 交互模式升级 · 设计方案 v0.2

> 状态：草案待评审（v0.1 2026-06-22 立项 / v0.2 2026-06-22 锁定引擎形态 + 补 AI 后台感知·触发·收件箱闭环）。本文是这轮交互重构的**设计权威**；动代码前以本文 + 各模块原设计文档为准。
> 一句话：**三模块 →「一个主战场（地图）+ 一个后台（确定性引擎 + 外部 agent）+ 一个出口（企业微信日历）」**。
> 引擎形态（v0.2 锁定）：江湖 = **确定性引擎（G64111 事实层 + PDE 纪律层）+ 唯一数据源(SoR) + 人审闸门**；**江湖自身不配大模型 Key**，需要 LLM 的解析/调研交给外部 agent 经 MCP；站内 LLM 适配器降级为可选、默认关闭的冷启动上料口。详见 §3.0。

---

## 0. 背景与目标

### 现状（三段式三模块，靠 `view` 状态 `wall/sandbox/planner` 全屏切换）

| 模块 | 组件 | 职责 |
|---|---|---|
| 关系地图 `wall` | `Canvas` + `Sidebar` + `WinTendencyPanel` + 顶栏一排操作 | **看清局势**（诊断） |
| 策略沙盘 `sandbox` | `StrategySandbox` = `EngineBar`（策略引擎局势栏）+ 策略泳道 + 里程碑泳道 + 信号汇总 | **推演打法**（中间桥） |
| 行动计划 `planner` | `DealPlanner` = 年/月/周日历 + 三类事件 + 商机泳道 + 阶段段 + 结果回填 | **排期执行** |

三段式逻辑自洽，但代价是：**销售要在三个全屏视图间来回切**——在地图上看清了，要切到沙盘才能落策略，再切到行动计划才能排期。思考被切割，「看清→想透→落地」的飞轮每转一圈都要换页。

### 目标（用户拍板的三点诉求）

1. **关系地图强化**：把策略沙盘的策略泳道、里程碑泳道等形式，**直接并入关系地图内的交互界面**；让销售**不离开地图就能加深思考、产出新想法和内容**。
2. **AI 后台自动化**：把机器该干的活**沉入仅由 AI 运行的后台**，结果作为提案推回，人异步审核。
3. **行动计划关联优化**：行动计划**直接对接团队真实在用的日历（企业微信）双向同步**，不再重复维护一个总览视角。

### 三项已决策（2026-06-22 对齐）

- **日历对接**：直接做**企业微信自建应用双向同步**（团队有企微资质，凭据走现有 BYO 加密模式）。
- **行动计划去留**：**退役年/月/周网格总览**；只保留①里程碑泳道（并入地图）+②轻量行动清单。
- **AI 后台范围**：**四项全部沉入后台**——荐关系/企查查建图、录音→情报提取、局势监控/支持度变更提案、策略/打法初稿生成。（AI 推演台 `StrategyConsole` 保持人工按需触发，不进后台。）
- **AI 后台引擎形态**：江湖核心 = **确定性引擎 + 外部 agent（经 MCP）为主，江湖自身免配大模型 Key**；站内 LLM 适配器（`voice.ts`/`suggest`/`strategy` 的 LLM 路径）降级为**可选、默认关闭**的冷启动兜底。理由与速度结论见 §3.0。

## 1. 宏观架构：人动脑 / 机器干活 / 排期外放

```
        ┌───────────────────────────────────────────────┐
        │            关系地图（人的唯一主战场）            │   ← 诉求①
        │   画布（局势真相）  ⟂  推演坞（局势栏+双泳道）   │
        │   选中人↔卡片双向高亮 · 不切页就能想透+产出      │
        └───────────────┬───────────────────────────────┘
                        │ 提案进收件箱（人审采纳才落库）
        ┌───────────────┴───────────────┐   ┌───────────────────────┐
        │   AI 后台引擎室（机器持续干活） │   │  企业微信日历（执行落地） │
        │   确定性引擎(局势/方案/缺口)    │   │  行动/里程碑 双向同步     │  ← 诉求③
        │   + 外部 agent 经 MCP(调研/解析)│   │  结果回填走录音→证据闭环  │
        │   → 统一变更提案层 + 审核收件箱 │   │                       │
        └───────────────────────────────┘   └───────────────────────┘
                        ↑ 诉求②
```

**收敛结果**：人只在**一个面**上工作（地图 + 一个收件箱），机器在后台跑，排期落在销售自己的企微日历里。
- 策略沙盘 → **被地图吃掉**（UI 并入，数据/逻辑零变）。
- 行动计划 → **大部分外化到企微日历**，残留（里程碑泳道、轻量行动清单、结果回填）也回归地图。
- `ViewTabs`（关系地图/策略沙盘/行动计划三选一）**退役**——不再有"三个模块"，只有一个工作台。

这套并非另起炉灶：它正是此前已对齐的「**机器写初稿·人审**」范式（统一变更提案层 + 审核收件箱）的落地形态，AI 后台 = 那条主线，本轮把它和"地图吸收沙盘""日历外放"一并收口。

## 2. 模块一：关系地图吸收策略沙盘 →「推演坞」

### 2.1 核心思路

把 `StrategySandbox` 的三件内容——**局势栏 `EngineBar` + 策略泳道 + 里程碑泳道 + 信号汇总**——从独立全屏视图，改造成关系地图**底部一个可上拉的「推演坞」**。画布（那张"牌桌"）**始终占据上方**、永远可见；推演这件事在下方进行。销售盯着局势真相想打法，而不是切到另一个页面凭记忆想。

推演坞**接管现在 `WinTendencyPanel` 的底部槽位**（趋赢力明细折进坞内现状锚的可展开区）。

### 2.2 三档高度（复用现有 `WinTendencyPanel` 的 grabber/fab 折叠语言）

| 档位 | 内容 | 画布占比 |
|---|---|---|
| **收起** | 一条**局势条** = `EngineBar` 收起态（姿态徽章 + 预期回报 + 赢面小字 + 趋赢力%） | 画布满屏，底部一条 |
| **半展开** | 局势条 + **策略泳道**（现状锚→策略卡→AI 候选虚位）+ **里程碑泳道**（倒推→终局锚） | 画布上 ~45%、坞下 ~55% |
| **全展开** | 上述 + **信号汇总**（全部缺口/风险/弹药/关键干系人）+ 录证据面板 + 推演方案 | 画布上 ~35% |

移动端（强制横屏，`OrientationGate`）：推演坞为底部 sheet，沿用 win-fab → 上拉 sheet 的现有模式。

### 2.3 让"不离开地图就能加深思考"成立的关键 = 画布 ↔ 推演坞双向联动

这是本模块的灵魂，不是把沙盘塞到底部就完事：

- **选中画布上的人 → 推演坞聚焦该人**：过滤出挂靠该人的策略卡、该人造成的缺口（`gaps.ts` 的 `computeGaps` 已能把评分缺口定位到具体人）、贡献分（`contribution.ts` 的 `personContributions`）。
- **选中推演坞里的策略卡/缺口 → 画布高亮目标人**（`StrategyCard.personId` 已有）。点缺口"＋"挂卡时，画布上对应的人脉冲提示。
- **从画布直接产出**：选中人 → 坞内一键"为 TA 定一张策略卡 / 排一个里程碑 / 录一条证据"，全部就地完成、就地落库（全走现有 `act()` → `mutate.ts` 通道）。
- **AI 候选就位**：后台生成的策略卡/里程碑/行动初稿，以**虚位卡**出现在泳道将落的位置（`StrategySandbox` 的 `fwdCands`/`bwdCands` + `EngineBar` 的 playbook 勾选采纳逻辑直接复用），采纳→落库、忽略→消失。

**与现有「详情抽屉」并存、不替代**（点击层次保持现有模型，只多挂一层坞聚焦）：

- **单击**卡片/连线 = 选中（出锚点/控制点）**＋ 推演坞聚焦**（轻量策略视角：该人的缺口/策略卡/贡献分）。
- **双击 / 选中后再点**（`secondTapOpens`）= 打开右侧**详情抽屉**——`DetailDrawer`（人物全字段：FORM/角色/支持度/BI/UCV/交往日志）｜ `EdgeDrawer`（关系全属性）。**现有命中逻辑一行不改**。
- 两者分工互补、不互相吃掉：**坞 = 这个人在局势/打法里的位置（看 + 想）**；**抽屉 = 这个人的完整档案与打分输入（编辑 + 录入）**。坞是浅层策略透镜、抽屉是深层全字段编辑。

诉求①(b)"产出新想法和内容"由此成立：**想（局势栏判断）→ 定（策略卡/里程碑）→ 录（证据）→ 采（AI 候选）全在地图一个面上闭环**，画布上的局势真相全程在眼前。

### 2.4 工程影响

- **近零 schema**：这是已有组件（`EngineBar`/泳道/信号汇总）的**重新布局**，数据与 Action 契约（`StrategyCard`/`OppMilestone`/`EvidenceEvent` 等）**完全不动**。
- 新建一个容器组件（暂名 `DeliberationDock`）承载 `EngineBar` + 两条泳道 + 信号汇总；`App.tsx` 的 `wall` 分支里，把 `WinTendencyPanel` 槽位替换为它。
- `StrategySandbox.tsx` 的泳道/抽屉 JSX 基本可平移进坞；`ViewTabs` 与 `sandbox` 分支删除。
- 双向高亮：复用 `App.tsx` 已有的 `selectedId` / `selectPerson` 选中模型，给坞传入 `selectedPersonId` + 回调。
- **画布/牌桌卡片零改动 —— 推演坞是纯增量**：沿用 `Canvas.tsx` 现有 168×92 拟物卡片（色脊/角色印章/G64111 逐人贡献分/支持度/FORM·完成度/失血·缺口·待核实·★P4 徽章，见 `docs/牌桌视图-设计方案.md`），不另造节点形态、不推倒五轮交互成果。**双击开详情抽屉（`DetailDrawer`/`EdgeDrawer`）、拖拽、框选、内联命名等命中逻辑全保留**（见 §2.3 点击分层）。原则=**基于现有原型增量改造、复用已落地的优点**（2026-06-22 用户明确）。
- **风险点最低、可见收益最高 → 排 P0 先做**。交互原型已过目（牌桌画布 + 底部推演坞三档 + 卡片↔坞双向高亮）。

## 3. 模块二：AI 后台引擎室 + 审核收件箱

### 3.0 引擎形态（v0.2 锁定）：确定性引擎 + 外部 agent，江湖免配大模型 Key

「AI 后台引擎」不是跑在江湖里的自主 agent，也不靠江湖自配大模型做解析。它 = **江湖端确定性引擎 + 外部 agent（经 MCP）+ 人审闸门**：

- **江湖端 = 确定性引擎**（纯函数、跑在前端/服务端、零模型成本、零开放联网、即时）：G64111 事实层（打分）+ PDE 纪律层（局势 `analyzeDeal`、方案包 `playbook.ts`、缺口 `gaps.ts`、证据→分布、支持度背离 `detectShifts`）+ 图算法荐关系（共同邻居）+ 企查查建组织图（数据 API，非 LLM）。
- **外部 agent = 自主调研/解析**（WorkBuddy/OpenClaw/Claude 等在江湖外跑，用自己的联网与模型能力）：把录音/纪要变成结构化的人和关系、语义层猜关系、联网找人——经 **MCP `propose_*`** 投候选进江湖候选层。这正是「机器写初稿·人审」六拍里「WB 后台提炼 → MCP 分轨写入」的形态。
- **站内 LLM 适配器**（`voice.ts`/`suggest`/`strategy` 的 LLM 路径）：**降级为可选、默认关闭**的冷启动上料口。接了外部 agent 的租户关着它走纯粹版；没接 agent、想站内即时抽一段纪要的，打开它兜底（带 mock 回退，零额外成本，代码不删）。

**为什么这么定**：① 四项后台功能里，**局势监控、打法初稿本就是确定性的**（PDE/`playbook.ts`，零 LLM），荐关系图算法、企查查建图也是——**真正吃 LLM 的只有「录音→建图」和「语义荐关系」两件，恰好是外部 agent 最该干的**。② 江湖不自建服务端 agent loop：用租户 Key 驱动多步循环成本/延迟不可控、合规（铁律②）更难守、且与外部 agent 能力重叠。③ 江湖定位更纯——**确定性引擎 + 唯一数据源 + 人审闸门，任何 agent 都能喂它**，而非又一个 AI 套壳。

**速度结论**：前台**更快**（确定性纯函数本地即算，无「推演中」转圈、无模型 API 等待）；需要 LLM 的解析变成**异步**——外部 agent 处理完把候选推进收件箱，人全程不被阻塞（正是「AI 后台」想要的非阻塞模型）。不是交互变慢，是结果异步到达；唯一体感差异="贴一段纪要立刻成图"变为"等 agent 处理完进收件箱"，但手动建人/边永远即时。

### 3.1 四项后台功能（按动力源重分类）

| 后台功能 | 动力源 | 落地 |
|---|---|---|
| 局势监控 / 支持度变更提案 | **确定性 PDE**（`detectShifts`） | 证据一变即重算、背离生成改分提案；零 LLM |
| 策略 / 打法初稿 | **确定性 `playbook.ts`** | 按缺口/终局生成方案包候选；零 LLM（E1.5 已砍 LLM 润色） |
| 荐关系（图算法）/ 企查查建组织图 | **确定性算法 + 数据 API** | 共同邻居荐边 + 企查查关键人；零 LLM |
| 录音→情报提取 / 语义荐关系 | **外部 agent 经 MCP**（站内 LLM 适配器可选默认关） | agent 提炼 → `propose_*` 投候选 → 收件箱 |

> 不进后台：`StrategyConsole`（🧠 AI 推演台）保持人工按需——销售主动发起的深度推演对话，不自动跑。

### 3.2 输出契约：统一变更提案层

所有机器作者（**江湖确定性引擎 + 外部 agent 经 MCP `propose_*` + 可选站内 LLM 适配器**）写入**同一个审核队列**——"一个审核队列，多个机器作者"。每条提案含：

- **类型**：新建人物 / 新建关系 / 字段更新 / 角色·支持度变更 / 策略卡 / 里程碑 / 行动初稿。
- **diff**：改前 → 改后（字段更新/改分必须可视化对比）。
- **溯源**：来源（engine/agent-mcp/qcc/voice）+ 证据/原文片段 + 置信度。
- **影响预览**：采纳后的后果，如「趋赢力 60% → 38%」「覆盖 1 个未覆盖缺口」（确定性引擎能预算，先算后采）。
- **操作**：采纳 / 改后采纳 / 驳回。

**分期落地**（守"小步"硬规则）：
- **v1（低/零 schema）**：先做**聚合视图**——把外部 agent 经 MCP 投的 `RelSuggestion`/`PersonSuggestion` + 确定性引擎的局势背离/方案包提案，聚合成 Hub 级收件箱 + 地图内联角标。复用现有 `SuggestionPanel` 的采纳/驳回，升级为带 diff、影响预览、批量、跨客户跨商机。
- **v2**：统一 `ChangeProposal` 表（字段级归因/批次回滚/采纳率统计）+ **字段级 human-wins**（人碰过的字段，机器下次同步降级为提案而非静默覆盖——补差距分析①的红线）。

### 3.3 零模型成本 · 租户上下文 · 调度

- **江湖侧零模型成本**：确定性引擎不用模型；外部 agent 用它自己那侧的模型额度；企查查走租户 BYO token（数据 API）。江湖核心**不需要配大模型 Key**，配置面更干净。（仅当租户主动开启可选站内 LLM 适配器，才用其 `AiConfig` BYO Key。）
- **租户上下文**：任何后台动作（确定性巡检 / 触发 agent / 接收 MCP 候选）都在**明确租户上下文**下、**按 `tenantId` 隔离**（铁律①）——后台化最大的安全面。
- **调度起步**：进程内轻量调度即可——确定性引擎本就随 state 变化即时重算（前端）；服务端只需**定时巡检**跑确定性规则（停滞检测/缺口扫描 → 推提醒提案）+ 在合适时机**触发外部 agent**。**先不引入消息队列**。
- **成本闸**：触发外部 agent 的频率/去重上限（避免反复让 agent 调研同一商机）。

### 3.4 触发与感知（引擎不可见，可见的是心跳与产物）

引擎是"内在发动机"，本身不可见——用户感知到的是它的**心跳**和**产物**，四层（由弱到强）：① **环境心跳**（Hub/局势栏角落"监测中 · 上次分析 3 分钟前"，不打扰）→ ② **提案到达**（收件箱角标 +1，主信号）→ ③ **就地呈现**（画布灰虚线候选、局势栏改分提示、推演坞 AI 虚位卡）→ ④ **收件箱**（全量批量审）。

触发三类：
- **事件驱动（主）**：录音/纪要落地、`ADD_EVIDENCE`（录证据/结果回填）、改角色/支持度、企查查导入、进久未看的商机 → 确定性引擎即时重算 + 必要时触发外部 agent 调研。
- **定时巡检（辅）**：每日对"活跃商机"跑确定性扫描（停滞/缺口），把"该动了"推进收件箱（如"这个 D 三天没碰，支持度该复查"）。
- **手动兜底**：「立即分析 / 让 agent 调研一下」按钮。

### 3.5 收件箱：界面与回流闭环

**界面**（视觉稿已过目）：Hub 级一个队列，每条是张**提案卡**——类型 + 一句话摘要 + 改前→改后 diff + 溯源（来源/证据/置信度）+ **影响预览** + 采纳/改后采纳/驳回；可按客户/类型/来源筛选 + 批量。提案同时在地图就地呈现（§3.4 第③层），不必每次跳收件箱。

**回流闭环（关键，机制已现成）**：采纳一条提案，**走的就是手动编辑的同一条路**——

```
采纳 → act() → api.mutate → mutate.ts 落库（带 origin + 溯源日志）
     → G64111 实时重算趋赢力（scoreFromDomain 读最新 state）
     → PDE 局势重判（analyzeDeal 读新 breakdown）
     → 可能产生新提案 → 回收件箱
```

例：采纳「钱大钧 支持→抗拒」= 一个 `SET_ROLE` 改 sentiment → 趋赢力立刻重算 → 局势从"稳步推进"变"先清再动" → 引擎可能荐新打法回队列。"结论性信息自动回流"的本质 = **采纳即写入、写入即重算、重算即再推演**，是飞轮不是单向灌数据。两条护栏：① 采纳带 `origin` + 溯源日志，可追溯（铁律②）；② **human-wins**——人确认过的字段，机器下次只能再发提案、绝不静默覆盖（v2）。

## 4. 模块三：行动计划 → 企业微信日历双向同步

### 4.1 定位

退役与销售自己日历重复的网格总览（`DealPlanner` 年/月/周视图）。**调度可视化交给企业微信日历**；江湖里只留**策略性的里程碑泳道**（已随模块①进推演坞）+ **轻量行动清单**（关联到人/商机的"下一步"，非日历网格）。

### 4.2 企业微信自建应用 · BYO 加密凭据

照 `QccConfig`/`AiConfig` 范式新建 **`WeComConfig`**（`tenantId @id`，AES-256-GCM 加密，**绝不明文落库/外发/入提交**，铁律④）：

```
WeComConfig { tenantId @id, corpId, agentId, secretEnc, updatedAt }
```

- 平台**不需要公司资质**——是**租户**用自己企业微信的自建应用凭据，江湖代调其 API。与微信登录/支付需平台营业执照是两回事。
- 前置条件（租户侧）：有企业微信 + 能建自建应用 + 开通**日历/日程**权限。这是接入门槛，需写入接入引导。

### 4.3 成员 userid 映射

江湖 user ↔ 企微 userid 必须绑定才能写对人的日程。新建 **`WeComUserBind`**（`tenantId` + `userId` + `wecomUserid`，租户隔离）：
- 方式 A：企业微信 OAuth 扫码授权自动绑（推荐）。
- 方式 B：团队面板里管理员手填映射（兜底）。

### 4.4 双向同步

新建 **`ScheduleSync`** 映射表（`planActionId`/`milestoneId` ↔ `wecomScheduleId`，`tenantId` 隔离）：

- **江湖 → 企微**：`ADD/UPDATE/DELETE_PLAN_ACTION`、`ADD/UPDATE/DELETE_MILESTONE` 落库后，调企微日程接口建/改/删日程。映射：标题、时间（`half` 上午/下午/晚上 → 时间段）、提醒、描述里带客户/商机上下文。
- **企微 → 江湖**：日程回调（webhook）或轮询 → 改期/删除回写 `PlanAction`/`OppMilestone`。
- **冲突**：复用已落地的**乐观锁 `version`** 思路（双向都可能改时间）——按 `baseVersion` 校验，不匹配以一方为准 + 提示；起步可对"纯时间字段"走 last-write-wins（无害）。
- 具体接口名/字段以企业微信日程 API 官方文档为准（实现期核对）。

### 4.5 留在江湖的部分

- **里程碑泳道**：随模块①进推演坞（它是策略——倒排/终局，不只是日程）。
- **轻量行动清单**：推演坞/侧栏里"本商机下一步行动"清单（点选编辑、标完成），**非日历网格**。
- **结果回填（飞轮闭环）**：主路径 = **录音→证据后台管线**（销售做完拜访→录音→后台提取结果→证据→局势演化→收件箱提案）；兜底 = 行动清单上的轻量"这次接触后态度↑/—/↓"（沿用 `DealPlanner` 现有 `outcome` → `newEvidence` 逻辑，迁到行动清单）。

### 4.6 退役与待定

- `DealPlanner` 的年/月/周网格 + 拖拽 UI 退役；数据（`PlanAction`/`OppMilestone`）保留并改为同步出去。
- **阶段段 `OppStage`（年视图）归宿待定**（见 §7）：它是商机阶段推进轨，既非日程也非策略泳道——退役随网格，还是折进商机头部/管线视图？
- **.ics 订阅**作为可选次通道（无企微成员/个人订阅），非主路径。

## 5. 数据契约与 schema 影响

| 变更 | 内容 | schema |
|---|---|---|
| 模块① 推演坞 | 已有组件重新布局，`StrategyCard`/`OppMilestone`/`EvidenceEvent` 等不动 | **零** |
| 模块② 收件箱 v1 | 聚合外部 agent(MCP) 候选 `RelSuggestion`/`PersonSuggestion` + 确定性引擎背离/方案包提案 | **零/低** |
| 模块② 提案层 v2 | `ChangeProposal`（字段级归因/回滚） | 新表 |
| 模块③ 企微 | `WeComConfig` / `WeComUserBind` / `ScheduleSync` | 3 新表 |

**硬规则对齐**：
- 新表全部**按 `tenantId` 隔离**（铁律①），照现有 `accountId` 冗余、无 relation、`@@index` 模式建。
- **不用原生 enum/json**（铁律③，SQLite↔Postgres 可移植）：类型/状态用 String，结构化数据用 String 存 JSON 文本（照 `Person.form` 现状）。
- 凭据 `secretEnc` 走 **AES-256-GCM**（铁律④）。
- 新增 Action 走前端 `store.ts` → 后端 `mutate.ts`/`types.ts` 同步（铁律⑤）；企微配置类走独立路由（照 `AiConfig`/`QccConfig` 不进 Action）。
- **G64111 引擎不动**（铁律⑥）：模块①是 UI 重排，局势/打分逻辑零改。
