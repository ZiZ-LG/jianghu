## 1. 产品定位与取舍

江湖 CRM 帮助个人大客户销售经理管理多个客户和商机，看清推进阶段、识别关键缺口，并持续落实下一步行动。

产品优先回答“先推进哪一单、卡在哪里、下一步如何取得进展”。“管理客户、线索、商机”是支撑对象；关系图、AI 和方法论围绕这一目标组织，不要求用户先学会一组独立工作台。

本次选择在现有核心上收敛体验。继续沿 G5–G7 扩张会增加不属于个人用户的维护负担；重写一套个人 CRM 会重复模型、迁移与安全基础。两者均不采用。

销售阶段、信息核实程度和成交概率分别表达：提交方案不代表预算已确认，六问填完不自动推进阶段，也不产生默认赢率。行动应能对应缺口，例如“请技术负责人引荐预算负责人”，而非只有“联系客户”。

## 2. 首版范围

| 范围 | 必须提供的结果 |
|---|---|
| 客户与联系人 | 查找客户、查看关键联系人与历史；一个客户可以有多个商机 |
| 线索 | 快速记录可能的机会，允许信息不完整；确认值得推进后延续记录、来源与历史，避免重复录入 |
| 商机总览 | 跨客户查看阶段、关键缺口、下一步与时间；搜索、筛选、手动重点标记 |
| 商机详情 | 集中呈现进展、关键人物、沟通记录与证据；明确显示未知和未核实信息 |
| 行动闭环 | 新建、完成、改期、取消；完成后记录结果、安排下一步或暂停商机 |
| 会后整理 | 手动记录始终可用；复用已有资料导入和 AI 候选速审，确认后更新正式数据 |
| 数据保障 | 私有账户、可靠保存、受权限约束的导出，以及现有审计、备份和恢复能力 |

默认导航为“商机、今日、客户”；快速记录作为全局按钮。“待判断”线索是商机中的视图，不引入一套重复的客户、联系人和转换历史。物理存储和阶段字段选择由后续权威盘点任务确定，本 ADR 不授权新增第二真相源。

无 WorkBuddy、无 G64111、无 AI Key 的用户仍能完成整个手动闭环。金额和目标日期允许未知，不用虚构值换取表单通过。首版不以固定 4–5 个商机作为产品配额；既有五商机 fixture 继续作为测试场景。

## 3. 现有能力处置

| 处置 | 能力 | 维护边界 |
|---|---|---|
| 保留并收敛 | Customer / Matter / Person / Relation / Commitment / Interaction-Evidence、多商机组合、来源、候选人审、基础导入 | 复用已完成的 G2–G4，不把已满足的能力重列为新开发 |
| 隐藏默认入口、按需使用 | 关系图、研究简报、假设、情报、关系雷达 | 嵌入具体客户或商机；既有数据可访问，敏感 ACL 和服务端授权继续执行 |
| 冻结新增 | G64111、PDE、协作模型、复杂权限配置、MethodologyPack 高级扩展 | 保留绑定、历史结果、必要回归、安全维护和恢复；不删除表、公式或数据 |
| 取消未来建设目标 | 团队协作产品化、组织层级、经理看板、团队预测、带教、企业方法论中心、Team/Enterprise 升级链 | 历史任务记录保留；不因取消路线而标记其已完成 |
| 后置且不排入首版 | 个人方法论上传、提取、发布和版本管理 | 先验证六问与日常闭环；后续需求成立再登记任务 |
| 从旧 Gate 中承接 | 权限矩阵、版本化 migration、备份恢复、审计、精确 SHA CI、发布检查及回滚 | 不能随 G5–G7 撤下；见第 7 节映射 |

隐藏是产品呈现变化，不等于禁用所有底层服务，更不等于移除鉴权。冻结是停止扩展，不停止安全、兼容和数据保全维护。取消是撤下未来目标，不是删除实现或历史。

## 4. 可选商机六问

以下六问参考 MEDDIC 的六类信息，采用日常中文表达，作为可跳过的检查提示：

1. 客户为什么需要解决这个问题，现在为什么要动？
2. 做成后有什么可验证的价值？
3. 谁能批准预算或采购？
4. 客户按什么标准选择方案？
5. 决策和采购要经过哪些步骤，关键时间是什么？
6. 谁愿意在客户内部推动，已有何种实际行动？

- 不强制填完，不默认计算总分或赢率，不将完整度当成阶段门；各项保留来源、更新时间和核实状态。
- 总览突出用户选定的关键缺口，六问在详情展开。缺口与验证行动相连，不另造一套与 Commitment 竞争的待办。
- 销售阶段由用户明确更新，允许回退、暂停和关闭；生命周期、销售进展和方法论评价各自语义清晰，存储仍遵守单一权威。
- AI 只生成带来源、证据与置信度的候选；无证据时标为未知，不填造引用。置信度不等于成交概率。
- 正式商机状态、关系、方法论结论和行动，只能通过用户命令或人审采纳事务更新；来源撤销、版本冲突和权限变化须重新校验。
- “逾期”“无下一步”等确定性读模型可以自动呈现，不自动改变正式状态。
- 复用 MethodologyPack 版本与绑定基础；不为六问开发通用公式语言、任意脚本、自动历史重评或企业发布中心，也不自动改绑历史 G64111/PDE。

未来个人方法论若获任务授权，先限定为私人问题清单和行动提示：AI 提取候选、用户确认、固定版本；不执行代码，不自动迁移或覆盖历史结论。本轮批准后置，不代表已批准该功能开发。

## 5. 私有账户与多租户边界

一个注册账户原则上对应一个私有租户，用户无需先配置团队或组织；tenantId 始终作为账户间隔离边界。

所有列表、按 ID 直查、搜索、聚合、AI 上下文、导入、人审、导出和写入继续经过 tenant scope、RBAC、effective resource scope；敏感内容再相交 creator/share ACL。隐藏团队入口不能为直接 API 请求放行。

现有同手机号或邮箱跨租户登录、协作租户和历史绑定需保全。此产品原则不等同于全局手机号/邮箱唯一约束；不得自动合并身份、搬迁租户数据、删掉旧成员，或取消存量授权校验。身份冲突预检与迁移需独立设计。

## 6. PostgreSQL 单一引擎目标与退出条件

已批准目标：开发、测试与生产的持续功能建设最终统一到 PostgreSQL。环境仍使用隔离数据库、凭据与测试/恢复目标；“单一引擎”不等于把所有环境放入同一个库，也不改变租户隔离。

当前实现仍为 SQLite schema 源文件生成 PostgreSQL schema，server 测试与升级脚本仍依赖 SQLite。不能仅删除 provider 分支、替换一个配置项或跳过测试就宣布完成。

顺序执行：

1. 盘点开发、测试、CI、运维脚本、历史数据和共享路径中的 SQLite 依赖，形成可验证的退出清单。
2. 确定 PostgreSQL schema 的唯一权威与现有 migration 衔接；完整验证新建数据库及现有数据库升级。
3. 迁移开发和隔离测试流程，确保 tenant scope、事务、约束、幂等与恢复矩阵不因换引擎丢失覆盖。
4. 核验 SQLite 存量保全、必要维护/显式迁移路径、备份恢复、应用与数据回滚；核实自我修养共享路径不受越界影响。
5. 以上条件全部通过并记录验收证据后，才能停止新增 SQLite 功能兼容要求。

**退出 Gate 之前，现有 SQLite/PostgreSQL 双库纪律保持有效，Prisma schema 不引入原生 enum/json。**引擎切换不顺带改变全部字段类型、删除旧 migration 或清理数据库。

已有加密 pg_dump 逻辑备份及隔离恢复脚本继续保留。它们不等于持续 WAL 归档、PITR 或已验证的异地灾备；本次没有核验任何生产备份调度。正式数据服务的最大可接受数据丢失时间与恢复时间须明确并实测，PITR 的前置时点由该目标决定，本 ADR 不预先宣称其已实现。

## 7. 研发顺序与安全职责承接

治理落盘 → 私有账户与核心权威收敛 → 商机/今日/客户体验及六问 → 个人销售闭环与安全验收。

数据库收敛单独分任务执行，可在现有 PostgreSQL 运维基础上推进，但同一时间仍最多一个 CRM 任务 IN_PROGRESS；不以数据库全面重写阻塞必要的体验验证，不以体验简化跳过数据安全 Gate。

| 旧任务/目标 | 新处置与承接 |
|---|---|
| SAAS-301～307 团队经营与带教 | 不再排入本产品建设；历史保留 |
| CORE-301 权限矩阵 | 现有角色、tenant/resource scope、敏感 ACL、撤销、直查、导出与聚合回归承接到 SAAS-215；不为测试创造新的经理功能 |
| CORE-401～406、SAAS-401～403 企业方法论 | 取消原企业路线；现有版本、绑定与历史保全继续，六问在 CORE-209/210、SAAS-214 范围内最小复用 |
| CORE-501/502 物理兼容层收缩 | 冻结排期；仅在消费者清零、存量核对和独立授权后执行，不作为首版必经重构 |
| SAAS-501 套餐升级 | 取消 Team/Enterprise 升级链；本账户数据导出与连续性承接到 SAAS-215 |
| CORE-503 备份恢复与安全总门 | 现有双库及 PostgreSQL 恢复/回滚门承接到 SAAS-215；切换后的完整矩阵和退出验收承接到 CORE-214 |
| SAAS-502 GA | 取消重型 GA 与套餐目标；发布身份、必要观测、受控验证、授权和回滚仍是 SAAS-215/后续实际发布的必过门 |

所有代码任务必须带 CORE/SAAS ID、小步提交；涉及共享契约、schema、算法和运维时执行相应额外检查。合入前核验候选精确 SHA CI，合入后核验合并结果精确 SHA CI，不能以旧 SHA、部分 job 或本地测试替代。

## 9. 验收与回滚

产品验收验证用户快速建档、隔日接续、跨客户选择先处理的商机、会后减少重复整理；需区分本地/CI 场景与真实用户观察，不把测试通过写成已验证留存或成交率。

治理回滚只撤销本任务文档提交，不涉及数据库恢复；原有 DONE 任务和状态历史完整保留。运行时的账号、阶段、方法论和数据库切换分别由所属任务提供独立回滚方案。
