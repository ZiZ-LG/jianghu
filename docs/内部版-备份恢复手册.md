# 江湖内部版：PostgreSQL 备份与恢复手册

适用范围：Docker Compose 部署的江湖内部版。数据库只在 Compose 私网内可达，任何恢复都必须先落到隔离数据库验证，禁止原地覆盖生产库。

## 1. 配置与安全边界

在被 Git 忽略的 `.env` 保存：

```ini
BACKUP_DIR=/var/backups/jianghu
BACKUP_RETENTION_DAYS=14
BACKUP_MASTER_SECRET=<openssl rand -hex 32 的输出，恰好 64 个十六进制字符>
```

- master secret 必须独立生成，不能等于 `POSTGRES_PASSWORD`；短值、占位值和非 64-hex 值会被拒绝。
- 脚本用域分离方式派生加密密钥和 MAC 密钥。payload 是 PostgreSQL custom-format 经 AES-256-CBC/PBKDF2-SHA256（600000 次）加密；`auth.hmac` 对 metadata 与密文做 encrypt-then-MAC，恢复时先验 MAC、后解密，`payload.sha256` 用于额外损坏诊断。
- secret 只从被 Git 忽略的 `.env` 读取，派生加密口令经文件描述符交给 OpenSSL，不出现在命令参数或日志。
- `pg_dump` 直接流入 OpenSSL，不产生明文 dump。每次结果先在隐藏工作目录完整生成并自验，再用一次同文件系统目录 rename 原子发布；进程锁和随机后缀避免同秒并发冲突。
- master secret 必须另行进入组织密码管理器，并与备份目录分开保存。丢失密钥等于备份不可恢复。

## 2. 创建与核验备份

```bash
cd /data/jianghu                 # Mac mini 按实际仓库目录
bash scripts/backup-postgres.sh
find /var/backups/jianghu -maxdepth 1 -type d -name 'jianghu-*.backup'
```

每个 `.backup` 目录是不可拆分的认证制品，包含 `payload.enc`、`metadata`、`auth.hmac` 和 `payload.sha256`。脚本从运行中 db 容器读取实际库名/用户/密码，并按 `BACKUP_RETENTION_DAYS` 清理过期的完整目录。部署脚本发现既有数据库时会在拉代码、build/up 前调用它；备份失败立即中止部署。

建议用受限权限的定时任务每日执行，并把完整 `.backup` 目录复制到受控异机介质。不要拆分目录，也不要只把备份留在数据库所在磁盘。

## 3. 恢复演练（只能到隔离库）

```bash
BACKUP=/var/backups/jianghu/jianghu-YYYYMMDDTHHMMSSZ-RANDOM.backup
bash scripts/restore-postgres.sh "$BACKUP" --database jianghu_restore_drill
```

恢复脚本按以下顺序失败关闭：

1. 在解析 metadata、解密或建库前验证 HMAC；错误密钥、metadata/payload 篡改均无数据库副作用。
2. 目标名必须匹配 `jianghu_restore_[A-Za-z0-9_]+`；无条件拒绝 `postgres`、`template0`、`template1`，并拒绝与运行中 db 容器实际 `POSTGRES_DB` 相同。调用方覆盖环境变量不能绕过。
3. 目标已存在时拒绝；只有明确追加 `--replace` 才允许重建该隔离库。
4. 解密流直接进入 `pg_restore`，无明文临时文件；失败会删除本次创建的半成品库。
5. 验证 `_prisma_migrations`、`Tenant`、`CommandRun`、`EvidenceEvent` 均存在。

需要重跑同名演练库：

```bash
bash scripts/restore-postgres.sh "$BACKUP" --database jianghu_restore_drill --replace
```

完成业务 smoke 后删除演练库（名称必须人工核对，绝不能写生产库名）：

```bash
DB_USER=$(docker compose exec -T db sh -c 'printf "%s" "$POSTGRES_USER"')

# 1) 独立连接终止演练库会话
docker compose exec -T db psql -v ON_ERROR_STOP=1 -U "$DB_USER" -d postgres -c \
  "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = 'jianghu_restore_drill' AND pid <> pg_backend_pid();"

# 2) 另一个独立连接删除演练库
docker compose exec -T db psql -v ON_ERROR_STOP=1 -U "$DB_USER" -d postgres -c \
  'DROP DATABASE "jianghu_restore_drill";'

# 3) 查询必须成功且结果为空；查询报错不能当成“已删除”
remaining=$(docker compose exec -T db psql -v ON_ERROR_STOP=1 -U "$DB_USER" -d postgres -tAc \
  "SELECT 1 FROM pg_database WHERE datname = 'jianghu_restore_drill'")
test -z "$(printf '%s' "$remaining" | tr -d '[:space:]')"
```

删除演练库时，终止连接与 `DROP DATABASE` 必须是两个独立 `psql` 调用；删除后再查询 `pg_database` 断言已不存在。生产替换只允许前缀受限的隔离库，绝不允许生产库。

## 4. 迁移、readiness 与故障处置

- `server/prisma/schema.prisma` 是唯一手编模型源；`npm run schema:postgres:render` 生成 PostgreSQL schema，`npm run schema:postgres:check` 检查漂移。
- 容器启动先扫描同步锚冲突，再执行 `prisma migrate deploy --schema prisma/postgres/schema.prisma`。从历史 `db push` 部署首次升级时，只有在线 schema 与 baseline 完全一致才登记 baseline；任何差异都拒绝自动接管。
- `/api/health/live` 只证明进程存活，不访问数据库；`/api/health/ready` 和兼容端点 `/api/health` 会执行数据库探针，失败只返回 `{"ok":false}` 与 HTTP 503，不泄露连接信息。
- 迁移失败时保留现有数据卷和部署前加密备份，先查看 `docker compose logs server`。不要用 `db push` 绕过，不要执行 `docker compose down -v`。

## 5. 每次发布的最低证据

记录 commit、时间和非敏感命令；至少保留：空库 `migrate deploy` 耗时、最新加密备份与校验结果、隔离恢复耗时、readiness、WorkBuddy/关键数据 smoke、演练库清理。M5 发布门只有在最近备份实恢复通过后才可签署。
