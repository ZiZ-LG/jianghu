# 江湖研发协作协议 v1

用户确认产品目标并验收可用成果；Agent 负责实现、技术审查、测试、修复和可回退交付。工程检查通过后，在已批准范围内自动继续。

本协议依据 [ADR-005](ADR-005-按功能批次自主研发与上线前数据基线.md)，是研发节奏、审批和上线前测试数据处理的唯一规则来源；产品范围仍按 [ADR-004](ADR-004-个人商机推进工作台与研发范围收敛.md)，状态只写入 [商业清单](商业版开发待办清单v1.md)。当前用户指令优先；旧计划、历史审批记录和 Skill 中的通用流程不能重新加回已取消的逐步审批。本协议不自动开启目标模式、创建新任务对话或授权并行 Agent。

## 1. 每次开始与恢复工作

1. 完整阅读当前工作区根 AGENTS.md，再读本协议、当前计划及商业清单的活跃部分；按需查看有关历史，不重复扫描全部旧记录。
2. 核对当前分支、工作区改动和需要依赖的主线/候选版本。保留无关文件，不在落后的工作区上覆盖已有方案。
3. 用简短说明确认本次沿用的目标、当前批次、验收结果及授权边界。已有明确授权时直接继续，不重复索要批准。
4. 新对话或另一模型必须实际载入这些文件；仅在过去聊天里说“记住”不能替代仓库规则。协议所在候选未合入 main 时，明确其生效工作区，不声称全局或主线已更新。

## 2. 按成果划分批次

一个批次交付一个可体验的完整流程，例如“商机地图查证 → 建立行动 → 今日接续”。内部子任务通常控制在 1–3 工程日；保留依赖和回滚点，但用户不用审核每个接口、字段和提交。

批次开始在现有计划中记录以下五项，不另建一套管理系统：

| 项目 | 应记录的内容 |
|---|---|
| 用户成果 | 完成后用户能做什么，复用哪些 C1–C7 场景 |
| 范围 | 任务 ID、必要修改区域、明确排除项 |
| 验证 | 本地检查、关键安全检查、适用的远程检查和体验步骤 |
| 交付 | 可打开的预览/产物、预期交付节点与回滚点 |
| 授权 | 允许的开发、测试和推送范围；main、部署及外部操作是否已有明确授权 |

用户已授权的计划包含上述内容时，Agent 自行整理即可。同一批次内必要的共享文件修改及缺陷修复属于既有范围；文件名单用于控制影响和冲突，不能每开始一个子任务就把相同授权作废。超出批次边界、影响另一条开发线或改变产品决定时才升级处理。

## 3. 自动推进和停止条件

Agent 自行完成文件拆分、实现选择、本地 commit、适用测试、代码复核、浏览器自测及缺陷修复。安全相关改动先说明影响，按计划补足验证；不能把代码正确性丢给用户审批。普通代码任务保留必要复核；鉴权、人审、迁移、加密和共享契约变化需要额外技术复核证据，增加 Agent 仍须有对应授权。

同一批次内，前置任务实现与适用本地验证完成后可以继续，不必逐任务推送、等待全量 CI 或合入 main。存在未解决的安全前置失败时先修复，不绕到依赖它的功能。批次交付时再集中完成适用的远程检查和最终复核。

需要用户决定时，只给出具体问题、影响、推荐方案和已准备好的可审阅结果：

- 产品目标、功能范围或验收口径发生实质变化，或预计工作量超过已批准批次的 30%。
- 新增费用、重依赖、敏感外发、外部平台绑定，或必要操作超出现有授权。
- 触碰明示排除区域，降低安全边界，或需要实际发布/破坏性操作而尚无授权。
- 调查后仍缺少必需信息，无法在现有范围内安全继续。

常规失败先自行诊断。外部服务瞬时错误每次最多自动重试两次；同一根因三次尝试仍失败时，不无限重跑，记录证据、改换可验证的安全路径，确需用户信息时再询问。优先重跑失败且需要复验的任务，不把全部 CI 重新启动当作默认修复。

## 4. 检查分层与精确版本

| 变化 | 本地及远程检查目标 |
|---|---|
| 纯说明文档/计划 | 范围、链接、历史记录与规则一致性；无需因文档修改重复运行未改变的业务/数据库套件 |
| 普通代码 | 类型、受影响模块及依赖消费者回归；界面变化跑实际交互，避免只用截图判成功 |
| 关键关联变化 | 权限、人审、共享契约、schema、事务、加密、依赖和运维变化扩大关联验证；保留 tenant scope、幂等、审计与相应恢复检查 |
| 实际发布 | 对拟发布的精确 SHA/产物完成完整适用检查、空库初始化、拟上线基线升级、备份恢复及回滚验证 |

文档是否轻量按用途判断；被构建、运行时或发布流程消费的 Markdown 不能只按扩展名跳过。检查选择应覆盖整个候选相对基线的变化和传递依赖；无法判定、检查器或工作流自身改变时扩大检查。依赖审计在依赖变化、实际发布及定期安全维护中保留，不能因业务代码未变而永久停止。

每个待交付候选的证据须绑定精确 SHA、实际运行和检查范围；旧 SHA 的成功不替代新 SHA。固定的必需汇总检查必须验证所有被选中任务的结果；选择器失败、必要任务未运行或被取消均不得伪装为通过。不要通过跳过整个必需工作流、关闭分支保护或标注虚假成功来减少耗时。

远程策略由 CORE-215 实现并验证：避免 push/PR 重复检查；仅取消同一开发候选中被取代的运行；正式发布不套用自动取消。复用现有 npm 缓存，先测耗时再优化；不为提速新增 Mac mini runner。CI 完成触发的共享发布链必须核对，main 检查变轻不能让生产误认为完整发布验证已通过。

**生效版本：** CORE-215 已在候选 `214a132493cb7717df637fee06a479951f4c4f1f` 实现分层，并由 [CI 33980069852](https://github.com/ZiZ-LG/jianghu/actions/runs/33980069852) attempt 1 验证；15 个任务成功，旧数据库演练按策略未选中，固定汇总通过。只对含该候选的工作区成立；main 尚未集成。纯说明文档不单独推送完整 CI；每次实际交付继续核对当次精确 SHA、选择范围与汇总，不能沿用本条的旧版本成功。

## 5. 提交、状态和用户交付

- 本地按可回退的小步 commit；相关提交按批次集中推送。一个批次默认一个 PR，不为每个内部步骤创建 PR。
- 代码和必要状态说明可在同一次交付中提交，不强制拆成“业务提交 + 治理提交 + 关闭提交”。CI 结果引用外部不可变记录，不再为写入“CI 已通过”反复改同一候选。
- 清单状态仍为 PENDING / READY / IN_PROGRESS / BLOCKED / DONE；同一时刻最多一个 CRM 子任务 IN_PROGRESS。DONE 表示该任务范围及约定验证完成，不表示已合入或已发布；旁列“本地验证、远程检查、用户验收、主线集成、发布”实际进度，未做明确记未做。
- 文档任务完成可以记录本地 DONE；功能批次只有适用技术检查完成才记录工程通过。子任务本地完成不允许把尚未通过的批次安全门或远程检查写成成功。
- 交付给用户：可打开的版本、3–5 条体验步骤、这次改善和已知限制。先由 Agent 走通，再请用户判断是否符合预期；沿用曹经理场景，不重复要求构造新 persona。
- 预览只使用明确隔离的测试环境和合成数据，并标明验证状态。没有正式发布授权，不部署到 lake2ocean.top、阿里云或 Mac mini。合入、上线和向他人发消息也不因用户验收通过而自动获得授权。
- 用户指出的批次内缺陷默认继续修复；新增需求按范围处理。目标模式中已授权的后续工作可以继续，但不能越过尚未确定的产品决定或安全前置。
- 进展消息说发现和下一步，不反复播报同一个 CI 等待状态。记录拿到预览的时间、重复 CI 分钟、用户决策次数和验收返工；不以 commit 数、测试数量或文档页数衡量产出。

## 6. 上线前数据库前提

项目所有者确认：尚未进入正式生产，现有 CRM 库均为假的测试数据，不需要将旧数据迁入新库。后续以空库初始化和可重复生成的合成 fixture 为基线，不安排旧假数据搬运、保全、身份合并或全历史版本恢复矩阵。

以下能力持续保留：版本化 schema/migration、从空库启动、账户隔离、人审、事务/约束、幂等、审计、加密、重启后持久化，以及拟上线基线的备份恢复与回滚。在引入真实用户/试用数据前明确恢复目标并实测；一旦存在真实数据，后续升级必须保护这些数据，不能继续援引本条清空。

旧测试数据可不带入新环境；这不要求删除旧库。需要重建时，仅操作任务内已核实身份的隔离测试库，不连生产、不扫盘清理，不删除用户文件、旧 migration 文件、G64111/PDE/协作实现或历史工程证据。SQLite 依赖切换仍由 CORE-211～214 验证，迁移开发/测试流程与迁移旧业务数据是两项不同工作。
