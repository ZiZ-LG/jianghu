# 架构 · 机制收敛路线图 v1

> 状态：已立项（2026-07-21，随 ADR-INT-502 批准）
> 性质：**本文件不授权动工**。每项动工前须在 `docs/内部版开发待办清单v1.md` 登记 INT 任务并按治理流程执行。
> 背景：2026-07-21 主线梳理确认后端存在多套「只加不拆」的并行机制。按 Owner 拍板（ADR-INT-502 决策 3），投产前只拆无风险项，结构性收敛在此立字据、按触发条件分期执行。

## 收敛项清单

### 1. 双评分引擎（g64111 趋赢力 + pde-kernel EV）

- **现状**：`packages/g64111`（趋赢力，前端/MCP/wecom/ai 消费）与 `packages/pde-kernel`（PDE/EV，`server/src/pde/` 消费、产 EVSnapshot）并行，各自有 golden/parity 测试纪律。
- **目标**：维持双轨（两者语义不同：事实评分 vs 决策纪律），但**展示层出口收敛**——界面上的"分数/建议"统一走 PDE 徽章单一路径，趋赢力降为明细页数据，消除"两个分数打架"的用户困惑。
- **触发条件**：商业版立项，或用户反馈两分数并示造成困惑时。
- **粗估**：3–5 天（纯前端展示层，不动内核）。

### 2. 五套候选/提案模型 → 统一候选表

- **现状**：PersonSuggestion（4 条写入路径）/ RelSuggestion（4 条）/ ChangeProposal / Reminder / EvidenceEvent(pending_review)，6 个写入方，由 `server/src/suggest.ts` 统一收件箱聚合读。
- **目标**：统一 `Candidate` 表 + `kind` 判别列（跨库可移植，不用 enum），写入方收敛到单一 helper；收件箱读侧从 5 表 JOIN 变单表查询。存量数据一次性迁移（版本化 migration）。
- **触发条件**：下一次收件箱功能迭代前（先收敛再加功能，避免第 6 套模型出现）。
- **粗估**：5–8 天（含迁移与全量回归）。

### 3. 三张 run 表（EnrichJob / CommandRun / SyncRun）

- **现状**：EnrichJob=异步队列（租约回收）、CommandRun=同步幂等重放、SyncRun=WorkBuddy 同步回执，语义有重叠。
- **目标**：评估并入 `CommandRun` + `kind`（异步任务=带租约字段的 kind），或至少统一幂等键与状态机词汇。
- **触发条件**：出现第 4 种 run 需求时（届时必须先收敛，禁止加第 4 张表）。
- **粗估**：4–6 天。

### 4. 两套写纪律（applyAction 无幂等 vs runCommand 幂等）

- **现状**：`/api/mutate → applyAction`（`server/src/mutate.ts`，Serializable 事务但无 CommandRun 幂等）与 `runCommand`（voice/recording/personMerge/compound 使用，幂等重放）并存。
- **目标**：mutate 的 action 逐个迁入 runCommand 幂等通道。**童子军规则**：每次功能迭代触碰某个 action 时顺带迁移它，不做大爆炸重写。
- **触发条件**：持续进行（每次触碰即迁移）；全量完成不设死线。
- **粗估**：单 action 0.5 天以内；全量约 10–15 天分摊。

### 5. legacy 清退包（2026-10，一个 INT 任务打包）

- **现状**：以下 legacy 均已标注废弃/存档，等 `LEGACY_SYNC_DEPRECATED_AFTER='2026-10-01'`（`server/src/mcpServer.ts`）到期。
- **清退清单**：
  1. MCP legacy 单实体同步工具（upsert_account/upsert_opportunity/append_visit_note 等 6 个，内部已转调 sync_intel_bundle）；
  2. `deploy-company-bootstrap-int501.sh` + `scripts/lib/bootstrap-marker.sh` 中仅 bootstrap 用的路径（marker 验证保留）；
  3. `server/prisma/postgres/legacy/20260712_pre_int501.prisma` 旧模型快照；
  4. `scripts/deploy-postgres-migrations.sh` 的 untracked/tracked 旧库接管分支（空库与已纳管分支保留）；
  5. `scripts/test-postgres-ops-integration.sh` 的 bootstrap 场景段。
- **触发条件**：2026-10-01 后，且确认无外部 agent 仍调 legacy 工具（看 SyncRun 来源统计）。
- **粗估**：2–3 天。

### 6. App.tsx 上帝组件重构

- **现状**：`app/src/App.tsx` 867 行 / 35+ state / 两大 return 分支重复渲染 6 个弹窗（InboxPanel 32 prop×2、RepairPanel、TeamBilling、AiSettings、HelpManual、McpAccess）；WeComSettings 只在 Hub 分支可达（作战室分支缺失，不对称）。
- **目标**：①重复弹窗簇提取为共享 `<GlobalDialogs>` 组件（顺带修 WeComSettings 可达性不对称）②35+ state 按域分组为 3–4 个 reducer（弹窗域/画布选中域/同步域/会话域）③InboxPanel 的 32 prop 收敛为聚合对象。
- **触发条件**：下一次前端功能迭代前先做（避免在上帝组件上继续堆叠）。
- **粗估**：3–4 天（纯重构零行为变化，浏览器回归全流程）。

### 7. 产品规划 Roadmap-v1 的处置

- **现状**：`docs/产品规划-江湖Agent协作生产系统与Roadmap-v1.md` 已入库，状态=战略提案待批准（未批准前不作为执行依据）。
- **目标**：Owner 批准/修订后，由其 R0–R5 派生下一份 superpowers 计划（接替 2026-07-11 内部版计划）；其 R0"可信生产地基"实质已随 INT-001~502 完成，批准时应先核对完成度再排 R1。
- **触发条件**：内部版 GO 之后，Owner 专项评审。

## 执行原则

- 一次只开一项（延续单 IN_PROGRESS 纪律）；每项动工前登记 INT 任务、TDD、跑全量收尾四件套。
- 收敛不改变安全边界：多租户隔离、AI 候选人审、BYO、幂等/审计语义在任何收敛中保持不变。
- 本文件由触发条件驱动，不由日历驱动；每完成一项在此打勾并记录 INT 编号。
