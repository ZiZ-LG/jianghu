## ST-001｜模型价格性能比正在重写企业选型账本

- 分类：AI 技术；结论范围：跨组织交叉判断；风险：high；时效：within_30_days
- 候选结论：OpenAI 调整 GPT-5.6 产品价格的同时，腾讯混元按不同模型公布差异化 Token 单价。企业选型正在从“最强模型”转向单位有效任务的综合成本。
- 至少两项事实：
  1. OpenAI 官方公告把 GPT-5.6 的降价与价格性能边界改善放在同一产品叙事中。（ST-001-e1）
  2. 腾讯云按混元不同模型公布每百万 Token 的差异化价格，并区分资源包与后付费顺序。（ST-001-e2）
- 再深一层：
  - 机制：模型分层和降价让更多任务跨过经济可行线，但失败重试与人工复核会把名义低价重新放大为真实任务成本。
  - 业务价值：按合格结果核算后，企业可以把模型投入与处理量、交付时长和毛利连接，减少只按 Token 采购造成的错配。
  - 适用边界：价格性能比不是稳定常数；任务难度、地区、上下文长度、容量和厂商调价都会改变结论，必须用客户任务集复测。
- 对销售个人的意义：报价讨论应使用“每个合格结果的总成本”，并同时展示基准模型、轻量模型和人工流程。
- 岗位与组织影响：销售、解决方案和财务需要共同维护成本假设，避免技术榜单替代客户自己的经济模型。
- 建议动作：选一个客户任务，分别计算模型费、失败重试、人工复核和容量保障，形成三档选型表。
- 核验说明：已按终审意见增加中国大陆厂商事实；价格属于高频变化信息，发布前须重新打开两方计费页核价。

## ST-002｜推理速度开始成为可单独采购的服务层

- 上轮意见处理：已落实“再深一层”：加入阿里云 Prime 快速模式作为独立厂商事实，并解释关键路径延迟如何影响完成率、产能与 SLA。
- 分类：AI 技术；结论范围：跨组织交叉判断；风险：medium；时效：within_30_days
- 候选结论：OpenAI 预览 Ultrafast 服务层，阿里云百炼 Prime 快速模式也将更高 TPS 作为单独计费能力。速度正在从模型附属指标变成可选服务等级。
- 至少两项事实：
  1. OpenAI 将 Ultrafast 作为预览服务层，并宣称 GPT-5.6 Sol 最高达到原服务 14 倍速度和每秒 750 个输出 Token。（ST-002-e1）
  2. 阿里云百炼把 Prime 快速模式作为单独能力，称 TPS 为标准 API 的 1.5 至 2 倍并按 Token 单独计费。（ST-002-e2）
- 再深一层：
  - 机制：实时任务中的每次等待都会延迟后续工具调用和人工决策；多步 Agent 流程还会把单步延迟串联累加。
  - 业务价值：更短等待可提高会话完成率、缩短坐席处理时长、增加单位时间内完成的工作循环，因此企业愿意为关键路径购买确定的速度等级。
  - 适用边界：离线批处理、低频任务或人工审核占主导的流程未必值得加速；若准确率、可用性或价格恶化，纯速度提升不能单独证明 ROI。
- 对销售个人的意义：不要只演示峰值速度；要把首 Token 延迟、持续 TPS、并发、稳定性和加速溢价写进同一验收表。
- 岗位与组织影响：AI 商业岗位需要把技术速度换算为等待时间、完成率、坐席产能和客户体验，而不是复述基准数字。
- 建议动作：为一个实时场景测算标准层与快速层对单次等待、每日完成量和单位任务成本的影响。
- 核验说明：已用 OpenAI 与阿里云两个独立厂商动作验证服务层现象；性能数字均为厂商自述，仍需客户负载实测。

## ST-003｜企业模型服务正在细化数据保留控制

- 上轮意见处理：已落实“增加第二事实”：加入 Anthropic 默认保留周期、例外与零保留安排。
- 分类：AI 技术；结论范围：跨组织交叉判断；风险：high；时效：within_30_days
- 候选结论：OpenAI 为符合条件的 API 客户提供 Zero Data Retention；Anthropic 公开默认保留周期、例外和可约定的零保留机制。数据边界正从一句承诺变成可谈判的产品与合同配置。
- 至少两项事实：
  1. OpenAI 公告称符合条件的 API 客户可使用 Zero Data Retention，并说明安全处理存在资格与配置边界。（ST-003-e1）
  2. Anthropic 隐私说明列出 API 输入输出通常在 30 天内删除，同时说明安全违规等例外及可签署零保留安排。（ST-003-e2）
- 再深一层：
  - 机制：可配置保留期把抽象隐私承诺转化为采购可检查的技术设置、合同义务和异常处理。
  - 业务价值：边界更清楚可减少安全问卷往返和法务不确定性，让原本因敏感数据停滞的场景进入受控试点。
  - 适用边界：零保留不自动覆盖客户端日志、第三方工具、违规调查或所有产品套餐；最终结论必须以客户合同和实际数据流为准。
- 对销售个人的意义：发现阶段要逐层确认输入、输出、日志、安全检测和删除，而不能把“不会训练”误写成“不会存储”。
- 岗位与组织影响：销售需要联动安全、法务和产品，建立数据流图、适用套餐、例外条款和持续核验责任。
- 建议动作：把一个场景拆成采集、传输、推理、日志、安全检测和删除六段，并为每段写责任人与证据。
- 核验说明：已增加第二家模型厂商的独立政策事实；本条只解释采购问题，不提供隐私或法律结论。

## ST-004｜多 Agent 协作要先把工作拆成可验证契约

- 上轮意见处理：已套用全批次新规则：至少两项事实、跨组织来源多样性、Agent 英文术语，以及机制—业务价值—边界分析。
- 分类：AI 技术；结论范围：跨组织交叉判断；风险：medium；时效：within_30_days
- 候选结论：Google Cloud 强调可验证子任务、成本匹配和最小权限；Anthropic 区分固定 Workflow 与自主 Agent，并建议先用简单、可组合模式。两者共同指向契约优先。
- 至少两项事实：
  1. Google Cloud 建议将目标拆成可可靠验证的子任务，并按成本匹配模型、限制数据权限、保留人类判断点。（ST-004-e1）
  2. Anthropic 区分预定义 Workflow 与自主 Agent，指出 Agent 通常以更高延迟和成本换取任务表现。（ST-004-e2）
- 再深一层：
  - 机制：任务契约把开放目标变成可观测接口，使错误可在单步被发现、重试或升级，而不是在终点才暴露。
  - 业务价值：可局部验收降低返工和审计成本，也让企业可以逐步扩大自动化范围而非一次承担全流程风险。
  - 适用边界：高度模糊、依赖隐性经验或缺少客观验收标准的任务仍需专家主导；增加 Agent 数量不会自动提高可靠性。
- 对销售个人的意义：演示应展示任务合同、失败处理和人工升级点，而不是把“自动完成”包装成不可审计黑箱。
- 岗位与组织影响：业务专家负责验收语义，工程负责运行边界，安全负责权限；三者缺一都会让 Multi-Agent 停留在演示。
- 建议动作：选择一个三步流程，为每一步写输入、输出、权限、验收人和失败升级条件。
- 核验说明：两篇官方工程材料来自不同厂商；方法建议不是统一标准，需在客户任务中验证。

  - 适用边界：并非所有辅助场景都应升级执行；高损失、低可逆或缺少客观验收的动作必须保留人类批准。
- 对销售个人的意义：机会判断要区分辅助、协作和执行三层，并为每次升级写出新增价值与新增控制。
- 岗位与组织影响：组织需要从工具培训转向工作设计、AgentOps、责任治理和持续反馈。
- 建议动作：把一个场景标为辅助、协作或执行，并写出升级到下一层所需的权限、评测和责任证据。
- 核验说明：国际采用叙事与大陆产品能力共同支持方向，但均不能证明所有企业已完成执行型转型。
