## 0. 评分总览

```
G64111 = G6-4-1-1-1，满分 100，称「趋赢力」
  6 必清(35) ＝ C1(10)+C2(5)+C3(5)+C4(5)+C5(5)+C6(5)
  4 优势(45) ＝ P1(5)+P2(10)+P3(20)+P4(10)
  1 决胜(20) ＝ 1K(20)
  + 1 套竞争策略(741) + 1 个行动计划（不计分，是动作产出）
```

- **趋赢力总分** = 6必清 + 4优势 + 1决胜
- **趋赢力百分比** = 总分 / 100，**允许为负**（用户决策 a）。理论区间 **−50% ~ 100%**
  - 最小值来源：6必清≥0、P1≥−5、P2≥−5、P3≥−20、P4≥0、1K≥−20 → 合计 −50
- 每次拜访后更新打分并存快照（趋赢力随情报/关系动态变化）

## 1. 角色模型（A / D / U / R / C）

> "ADURC" 是统称简写，实际 **5 类角色**。竞争对手**不是角色**，用支持度 `x` 标记客户方倒戈者；友商作为独立实体进入 741 竞争分析。

| 角色 | 名称 | 销售罗盘映射 | 细分码 | 能源客户典型岗位 |
|---|---|---|---|---|
| **A** | 批准人 | EB 经济购买影响者 | E-DB 终决策 / E-PB 建议决策 | 集团/二级单位主要领导、分管副总、CIO/总会计师 |
| **D** | 拍板人 | 本项目决策人 | — | 信息化部/财务部/工程管理部/新能源事业部负责人 |
| **U** | 使用者 | UB | U-WB 直接使用 / U-BB 应用受益 | 项目部/场站成本、计划、工程、物资、安全岗 |
| **R** | 影响者·技术把关 | Technical Buyer | T-CB 标准把关 / T-FB 预算支持 / T-AB 流程审批 | 信息化技术专家、招标采购中心、外部评标专家 |
| **C** | 教练 | Coach | C-CO 指导教练 / C-CA 内部倡导 | 业务/信息化骨干、设计院/咨询、总集成商 |

```ts
type Role = 'A' | 'D' | 'U' | 'R' | 'C';
type RoleSub = 'E-DB'|'E-PB'|'U-WB'|'U-BB'|'T-CB'|'T-FB'|'T-AB'|'C-CO'|'C-CA';
```

**教练五级**（C 的成熟度，🟡产品作为标签，不直接计分）：①提供有效信息 ②提供独特信息 ③评估关键人 ④提出行动建议 ⑤全面互动（最高）。
**信息可信度·四程度**：共识 > 明确 > 推理 > 不清（用于判断某项情报是否够格计分，见 P1）。

## 2. 支持度标尺（情感温度）

| 符号 | 含义 | 细分值 | 名称 |
|---|---|---|---|
| `☆` | 顶压力公开**排他性**支持（最高）| — | （P3/P4/1K 专用档）|
| `+` | 明确支持 | +1~+5 | 认可认同/有兴趣/支持/大力支持/热情拥护 |
| `=` | 中性 | 0 | 中立 |
| `?` | 未知/应该不会拒绝 | 0（**不计分**）| — |
| `−` | 负面/抗拒 | −1~−4 | 不感兴趣/作负面评价/抗拒你的建议 |
| `x` | 支持竞争对手 | −5 | — |

```ts
type Sentiment = 'star' | 'plus' | 'neutral' | 'unknown' | 'minus' | 'x'; // ☆ + = ? − x
// 细分 −5~+5 单独存 sentimentValue?: number（用于细粒度展示，计分以符号档为准）
```

> 注：宝典细分标尺跳过 −3（−2 直接到 −4），按原文保留。`=` 与 `?` 都是 0 分，但语义不同（中立 vs 未知），产品要分别存储与可视化。

## 3. 6 必清事项（35 分）

### C1 客户项目组织结构图 + D 的 FORM 表（10）

```
C1 = ADURC图分(满7) + D家庭FORM分(满3)

ADURC图分(满7) = 角色完整性分(满6) + 招采三类分(满1)
  · 角色完整性分 = 6 − 3·(A/D/U/R/C 任一缺失?1:0) − 1·(非A角色中倾向性为"?"的人数)，下限0
  · 招采三类分 = 1 × (采购负责人/招标代理或集采/甲方代表 已识别的类数 ÷ 3)

D家庭FORM分(满3) = max(0, 3 − 缺失问数)，家庭7问=籍贯/年纪/生日/毕业院校/配偶/子女/父母
```

```ts
function scoreC1(orgChart, dForm): number {
  const rolesMissing = ['A','D','U','R','C'].some(r => !orgChart.has(r));
  const unknownNonA = orgChart.people.filter(p => p.role !== 'A' && p.sentiment === 'unknown').length;
  const roleScore = Math.max(0, 6 - (rolesMissing ? 3 : 0) - unknownNonA);
  const procureScore = (orgChart.procurementKeyTypesIdentified / 3) * 1; // 0~1
  const adur = Math.min(7, roleScore + procureScore);
  const formFilled = dForm.filledOf7;          // 0..7
  const formScore = Math.max(0, 3 - (7 - formFilled));
  return adur + formScore;                       // 0..10
}
```
> ✅ 已定稿规则：① "角色缺失扣3"＝**只要有任一角色缺失，扣一次 3 分**（非每缺一个扣3）。② 招采三类"整体占1分"＝**按已识别类数比例**给分（识别 2/3 → 0.67）。③ FORM 家庭7问/3分采用**宝典原文严格曲线** `max(0, 3 − 缺失问数)`（填<4问即0分）；此曲线在 `ScoringProfile.curves.formC1` 中可切换为线性 `round(3×filled/7)`，默认 `strict`。

### C2 拍板人 D 的燃眉之急 BI（5）
```
C2 = 能明确陈述 D 的私人/紧急 BI ? 5 : 0
```
> BI 类型（能源版）：数字化转型考核压力、降本增效 KPI、按期投产、审计巡视整改、个人晋升、安全质量责任、投资风险、融资上市规范。

### C3 立项材料 + 项目排序（5）
```
7项 = 立项原因/项目名称/项目预算/实施计划/资金来源/项目排序/采购方式
C3 = max(0, 5 − 缺失项数)
```

### C4 介入项目阶段（5）— 越早越主动
```
需求调研立项=5 · 方案/可研编制上报=4 · 预算(概算)批复/资金申报=3 · 招标方案论证=2 · 招采执行=1
```
> 注意：C4 是「介入时机」评分项，**与商机管线阶段（线索→…→合同双签）是两回事**，不要混用。

### C5 招采事项（5）
```
5项 = 竞标方名单/家数 · 招标参数 · 评标规则 · 甲方项目代表 · 招标代理机构
C5 = max(0, 5 − 缺失项数)
```

### C6 UCV：D 的 BI 解决程度（5）
```
C6 = 已落地解决 ? 5 : (建议并获客户认可 ? 3 : 0)
```

## 4. 4 优势要素（45 分）

### P1 项目组多数人支持（5，区间 −5~+5）
```
仅计入「明确(及以上)确认」的倾向（四程度≥明确）；推理/不清一律不计   ✅
P1 = clamp( count(+/☆) − count(−/x) , −5, +5 )    // =/? 不计
```

### P2 招采关键人支持（10，区间 −5~+10）
```
采购/招标管理部门负责人(占4)：密谋4 / 口头承诺1 / 未有效接触0
招标代理或集采平台负责人(占2)：密谋2 / 口头承诺1 / 未有效接触0
甲方项目代表(占4)：          密谋4 / 口头承诺1 / 未有效接触0
若三类均"未有效接触" → P2 = −5
否则 P2 = 三项之和

判定：密谋＝私下密谋招标参数/评标规则且对方同意并落实使用；口头承诺＝私下沟通且对方同意采用有利我方的评标策略；未有效接触＝未私下沟通过。
```

### P3 与拍板人 D 密谋/明确支持（20）
```
计分：☆ +20 / + +10 / =? 0 / − −10 / x −20
"+" 判定（可私下约见，满足≥2条）：①共同策划项目预算 ②提供客户内幕 ③共同制定招标文件 ④提供对手情报 ⑤引荐1K或4P ⑥帮助控制项目进度
"☆" 判定（有压力不退缩）：事实证明法可不满足下列2条；假设证明法需满足≥2条：①指导下一步工作 ②确定有利我方的商务/技术要求 ③排他性推荐我方 ④确定有利我方的采购形式 ⑤指导报价 ⑥协助解决A/D的BI
```

### P4 关键影响人密谋/明确支持（10，下限 0）
```
计分：☆ +10 / + +5 / 其余(=?−x) 0     // P4 不为负
关键影响人判定：①在项目组 ②非A/D ③对A/D决定有影响，或是招采关键人
约束：A/D 已是 ☆ 则无需再找；同一时间只锁定一个（优先D的）；前期找"能影响决策"的、招采阶段找"能推动定标"的
```

```ts
const P3_1K_MAP = { star: 20, plus: 10, neutral: 0, unknown: 0, minus: -10, x: -20 };
const P4_MAP    = { star: 10, plus: 5,  neutral: 0, unknown: 0, minus: 0,  x: 0  };
```

## 6. 多 A / 多 D 聚合规则（用户决策 c：取中位数的低分）

```ts
// 每个 A 各自算 1K 分、每个 D 各自算 P3 分，再聚合
function aggregateLow(scores: number[]): number {
  if (!scores.length) return 0;
  const s = [...scores].sort((a, b) => a - b);
  const n = s.length;
  return n % 2 === 1 ? s[(n - 1) / 2] : s[n / 2 - 1]; // 偶数取偏低的下中位数
}
// 例：[+10,+20]→+10 · [−10,0,+20]→0 · [−20,−10,+10,+20]→−10
```
- 同理，若某项目存在多个"拍板人 D"，P3 = `aggregateLow(各D的P3分)`。
- 集体决策（党组会/董事会）= 多个 A，1K = `aggregateLow(各A的1K分)`。
- 🟡产品需支持"标记某角色为集体决策"，并把成员逐个评分后聚合。

## 7. 趋赢力总分、百分比与 741 竞争策略

```ts
function winTendency(s): { total:number; percent:number; band:Band } {
  const clears = s.C1 + s.C2 + s.C3 + s.C4 + s.C5 + s.C6;           // 0..35
  const priorities = clamp(s.P1,-5,5) + s.P2 + s.P3 + s.P4;        // -30..45
  const key = s.K1;                                                 // -20..20
  const total = clears + priorities + key;                          // -50..100
  const percent = total / 100;                                      // 允许为负 (a)
  return { total, percent, band: band741(percent) };
}
```

**741 竞争策略带**（用户决策 b：删除 25–50% 的"参考采购周期"条件）：

| 趋赢力% | 态势 | 可选策略 | 数字能源打法 |
|---|---|---|---|
| **≥75%** | 绝对优势·可承诺 | 直接赢单 | 控节奏、加速签约、绑框架/多项目复制、防节外生枝 |
| **50–75%** | 相对优势·可争取 | 制定规则/加速进度/总包 | 主导技术参数与评分；推动尽快挂网；联合体/总集成绑定设计院 |
| **25–50%** | 相对劣势·可参与 | 改变规则(A→B/A→A±1)/减速拖延/拆包 | 把客户从"比价格"引到"比一体化管控/降本实效"；拖到有利时点；拆出对手强项模块单独招 |
| **<25%** | 绝对劣势·重新复盘 | 重新回炉 | 评估放弃或养单；优先补 C1/C2 与 D/A 关系；争下一期 |

```ts
function band741(pct: number): Band {
  if (pct >= 0.75) return 'ABSOLUTE_ADVANTAGE';
  if (pct >= 0.50) return 'RELATIVE_ADVANTAGE';
  if (pct >= 0.25) return 'RELATIVE_DISADVANTAGE';
  return 'ABSOLUTE_DISADVANTAGE';
}
```

## 8. 可配置评分档案（用户决策 f）

```ts
interface ScoringProfile {
```

## 10. 关系网（L1–L4）↔ G64111 接口（用户决策 d）

G64111 是**纵向**（人对项目/我方），关系网是**横向**（人对人）。关系网服务于三件事：

| 用途 | 算法 | 反哺评分项 |
|---|---|---|
| **找 P4 关键影响人** | 在 L2(决策权力)/L3(情感) 边中，找出指向 D/A、自身非 A/D 的节点 → 候选关键影响人 | P4 |
| **找引荐路径打通 1K** | 从"我方已搞定(+/☆)节点"沿正向边(引荐/盟友/师徒/校友)到 A 做最短路径搜索 → 推荐引荐路线 | 1K |
| **企查查识别 x 风险** | 企查查关联(友商法人/股东 与 客户方人的亲属/共同任职) → 自动标记潜在 `x`(倒向对手)节点 | P1/P2/P3/1K 的负分预警 |

```ts
function findP4Candidates(g, opp): Person[] {        // 影响 D/A 但非 D/A
  const targets = opp.people.filter(p => p.role==='D'||p.role==='A');
  return g.nodes.filter(n => n.role!=='D' && n.role!=='A'
    && g.edges.some(e => e.layer in ['L2','L3'] && e.target===n.targetsOneOf(targets)));
}
function referralPathsToA(g, opp): Path[] {          // 我方支点 → A 的引荐链
  const won = opp.people.filter(p => ['plus','star'].includes(p.sentiment));
  const A = opp.people.find(p => p.role==='A');
  return shortestPaths(g, won, A, { allowEdge: ['引荐','盟友','师徒','校友','同门'] });
}
```

## 11. BI / UCV 数据结构

```ts
interface BurningIssue {           // 燃眉之急（可挂任意关键人，主要 D，也可 A）
```
